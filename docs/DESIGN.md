# 规则设计与边界

## 它管什么

四组，按使用顺序：

1. **该不该写**——7 级阶梯（需要存在吗 → 已有实现 → 标准库 → 平台原生 → 已装依赖 → 一行 → 最小实现），读懂需求和调用链之后才爬。
2. **怎么算过度**——可数判据替代形容词：三次才抽象、开关未切换即删、抽象需 ≥2 个今日实现、测出性能问题前不加缓存。
3. **怎么做事**——多步任务先出计划、任务多就派子代理、模糊就问不要猜。
4. **什么时候算完成、算能提交**——先跑出本轮证据再声称状态；提交要用户确认、文档到位、全量测试跑过。

外加一条不可协商的下限：已知失败模式必须处理，非平凡逻辑留能跑的检查，修 bug 打根因。

## 它不管什么

- **不提升质量上限。** 它减少垃圾，不生产好东西。算法、架构品味、性能优化都不在射程内。
- **不替你做边界判断。** 性能关键、并发安全、硬件校准这类场景下，"最小实现"倾向要让位给边界正确性；让位多少得自己判断，规则只写了「不参与偷懒权衡」。
- **压不住"留检查"。** 这是全套规则里执行率最低的一条，18 个样本里超过一半没留下可复跑的检查。

## 每条条款的由来

条款只从两处来：上游（见 `provenance.md`）或实测暴露的具体失效（见 `benchmark.md`）。

- **标准库缺位时的陷阱**——"标准库优先" + "不加依赖"在库无对应物时会反向逼出手写实现。这是实测出来的反向效应，不是理论担忧。
- **不发明需求**作为独立禁令——因为所有对照组都在发明，而需求只有一句话。
- **"留检查"按项目分档**——用来消解与 TDD 类规则"无例外先写失败测试"的直接冲突。
- **证据闸门**——因为出现过"声称验证过但没留痕迹"和"agent 报告成功"两类不可核对的说法。

## 已知失效点

**1. 规则越长，单条遵守率越低。** 三轮 18 样本的均值、方差与归因假设写在 `benchmark.md` 的「对规则长度的启示」，此处不复述数字。

**2. 检查留存率低。** 见上。

**3. 只在一种任务上被验证过。** CSV 求和能暴露边界处理与过度设计，但重构、并发、性能、跨文件改动都没测。规则里新增的提交纪律、计划格式、评审接收在这个任务里完全没有出场机会。

## 和其他规则集怎么选

- 只想省代码、少写无关功能 → 用 ponytail，实测它在这一维上更好。
- 需要管住交付流程（什么时候不能提交、什么时候必须问、什么算做完）→ 用本规则，接受它在省代码这一维上略差。

两者不冲突，但**不要同时常驻**：内容重叠，且会进一步加长上下文。
