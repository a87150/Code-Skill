# Code-Skill

一套给 AI 编码 agent 用的工程判断规则。核心理念只有一句：**不发明需求，不写没有检查的实现。**

规则本身是四个来源的综合：ponytail 的决策阶梯、codingskills 的可数判据、Superpowers 的行为闸门，外加实测暴露出来的补丁。

## 里面是什么

| 文件 | 用途 |
|---|---|
| `AGENTS.md` | 常驻规则。放到项目根目录或 `~/.dsh/AGENTS.md`、`~/.claude/AGENTS.md` 这类全局位置，每轮自动进上下文 |
| `skills/engineering-judgment/SKILL.md` | 同一份规则的 skill 版（带 frontmatter），放进 `~/.agents/skills/engineering-judgment/` 按需加载 |
| `docs/benchmark.md` | 对照实验的完整数据、三次复现、测量口径与全部修正记录 |
| `docs/provenance.md` | 每段规则的来源、上游许可证、哪些条款是实测新增 |

两种用法可以并存，但**别同时启用**：常驻版和 skill 版内容相同，同时生效等于把同样的规则喂两遍。

## 它解决什么问题

一句话需求，无规则时的产物：

```
"读 CSV，求 amount 列数值之和。文件来自第三方导出，质量不可控。"
→ 295–491 行代码，支持 UTF-16 编码探测、分隔符嗅探、货币符号、千分位、
  会计括号负数、科学计数法、Excel sep= 指令、options 参数……
```

同一句话，加规则后：

```
→ 39–90 行，只读逗号分隔，脏值跳过，缺列报错。
```

代码量差约 6 倍。

## 规则管什么、不管什么

管四件事：

1. **该不该写**——7 级阶梯，从"这功能需要存在吗"一路问到"能不能一行"。
2. **怎么算过度**——用可数的判据（出现三次才抽象、从未切换过的开关就该删），不用"保持简洁"这种形容词。
3. **怎么做事**——多步任务先出计划，任务多就派子代理并行，模糊就问不要猜。
4. **什么时候算完成、算能提交**——先跑出本轮证据再说；提交要用户确认、文档到位、全量测试跑过。

不管三件事：

- 不提升算法质量、架构品味、性能优化能力。它只减少垃圾，不生产好东西。
- 在性能关键、并发安全、硬件校准这类场景，"最小实现"倾向要让位给边界正确性——规则只写了「不参与偷懒权衡」，判断权还在使用者。
- 它压不住"留检查"这一条。实测 18 次里超过一半没留下可复跑的检查。这是全套规则里执行率最低的一条。

## 数据

同一任务、同一模型、prompt 对称，只有规则不同。跑了三轮，每轮每臂 2 次独立会话，共 18 个样本：

| 臂 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 均值 |
|---|---|---|---|---|
| 无规则 | 452 / 491 行，发明 5 / 6 | 402 / 295 行，发明 5 / 2 | 325 / 406 行，发明 4 / 4 | **395.2 行，4.33 项** |
| ponytail | 71 / 62 行，发明 0 / 0 | 69 / 90 行，发明 0 / 1 | 52 / 58 行，发明 0 / 0 | **67.0 行，0.17 项** |
| 本规则 | 39 / 90 行，发明 0 / 1 | 57 / 88 行，发明 1 / 1 | 82 / 70 行，发明 1 / 0 | **71.0 行，0.67 项** |

十八个样本，**零崩溃**，六组对抗输入（空值、脏字符串、BOM、仅表头、引号含逗号、缺列）全部给出合理结果。

三个结论，按可信度排序：

1. **规则对无规则是数量级优势。** 395 行 vs 67–71 行，约 6 倍；发明项 4.33 vs 0.17–0.67。六次样本无一例外。
2. **ponytail 比本规则更少发明需求，而且三轮方向一致。** 行数 67.0 vs 71.0，发明项 0.17 vs 0.67。这不是噪声——三轮六次里 ponytail 每次都不差于本规则。本仓库不提"比 ponytail 更好"。
3. **方差仍然很大。** 同一份规则三轮跑出 39、57、82 行。

为什么更全面的规则反而在这一维上更差？最可能的解释是：**规则越长，单条被遵守的概率越低**。ponytail 只有一条主线（能不做就不做），3048 字节；本规则 15 节、7382 字节，注意力被摊薄。另外本规则里"标准库缺位时"那节给了手写解析器一个正当性出口，而 ponytail 没有这段。

那本规则凭什么存在？不靠这个任务。CSV 求和只测"会不会过度设计"，而本规则比 ponytail 多出来的部分——提交纪律、证据闸门、调试流程、计划格式、评审接收——在这个任务里没有出场机会。它们解决另一类问题，目前只有案例，没有数字。

测量方法：发明项 = 10 项需求外特征的正则命中数，**匹配前剥离注释**。不剥的话，代码里"不做分隔符嗅探"这类否决性注释会被误算成"做了分隔符嗅探"，这一错误曾污染过前两轮数据。

## 来源

综合并改写了三个 MIT 项目：

- [ponytail](https://github.com/DietrichGebert/ponytail) — 7 级阶梯、根因修复、`ponytail:` 天花板标注
- [codingskills](https://github.com/JordanCoin/codingskills) — 三次才抽象、删除判据、YAGNI 的四条边界、与 DRY 的冲突裁决
- [superpowers](https://github.com/obra/superpowers) — 证据闸门、调试纪律、计划格式、评审接收

许可证与逐条归属见 `docs/provenance.md`。

## 一句话

这套规则不能让你比 ponytail 更省代码，它换来的是**更宽的行为约束**：知道什么时候不能提交、什么时候必须问、什么时候算做完。省代码那一维，用 ponytail 就够。
