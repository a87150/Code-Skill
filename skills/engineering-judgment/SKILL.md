# 工程判断规则

## 写代码前，按顺序停在第一个人站得住的台阶

1. 这功能需要存在吗？不需要就直接说清为什么不做。
2. 仓库里已有实现或模式？复用。
3. 语言标准库直接有？用。
4. 平台原生能力覆盖？用。
5. 已装的依赖能解决？用。
6. 能写成一行？一行。
7. 都不成立，才写最小实现。

阶梯是在理解问题之后才爬的：先读完需求和相关代码，把真实调用链走通，再决定哪级站得住。
不理解问题就选最小 diff，那不是效率，是第二个 bug。

## 多步任务先给计划

改 3 个以上文件、或跨会话才能完成时，先出计划再动手。

计划是写给没见过这个代码库的人看的。他猜不到的是**你的决定**，所以必须写清：建或改哪些文件、
每个文件负责什么、关键函数名与签名、规格里的具体值、每个任务由哪个测试证明。

一步 = 一个动作 + 可检验结果。"完成后端"不算步骤，"写出会失败的测试"算。
任务按"能否被独立否掉"切分：一个任务一个交付物加它自己的测试，
只在 reviewer 可能否掉一个而批准另一个的地方切开。

2 个以上互不依赖、无共享状态的任务并行做，不要串行。各自划分不同产出目录——
写冲突的并行等于没并行。

## 判据：可数、可验，不用形容词

- 第一次重复直接写，第二次记下，第三次才抽抽象。
- 开关从未切过、配置从未改过、参数从未传过非默认值 → 删。
- 抽象需 ≥2 个今天的真实实现，否则不建接口。
- 测出性能问题之前不加缓存。
- 为"以后可能需要"加的列、表、扩展点、事件总线 → 不建。
- 两个 stdlib 写法一样长时，选边界正确的那个。省代码不是选更脆的算法。

## 不可协商的下限

- 已知失败模式必须处理：无效输入、网络失败、写盘失败、空值、边界索引。来源不可控的数据（第三方导出、用户上传）尤其如此。
- 非平凡逻辑必须留下一个能跑的检查。项目已有测试设施（test script / pytest / 已有 test 目录）→ 走 TDD，先写失败测试；没有 → 3–5 行断言或自检脚本，不引入框架和 fixture。标准：删掉这个检查，有人能改坏这段逻辑还全绿，就是没留。
- 修 bug 打根因：grep 出该函数所有调用方，一次改共享函数。只修报告点名的那条路径，等于留下同源的第二个 bug。
- 安全、可访问性、会丢数据的错误处理，不参与"偷懒"权衡。

## 声称任何状态之前，先拿到本轮证据

没有本轮跑出来的输出，就不能说"通过""修好了""完成"。

1. 想清楚哪个命令能证明这句话。
2. 完整跑一遍，不复用上一轮的输出。
3. 读完整输出、退出码、失败数。
4. 支持才说；不支持就说实际状态，不许换成模糊说法。

禁用措辞：应该能过、大概没问题、看起来正常、上次跑过了、只跑了一部分。
agent 报告成功不是证据——查 diff、跑测试、看结果，再转述。

交付前拿需求逐条对：规格里每一条，是哪行代码、哪个测试满足的。对不上的就是没做完。

## 调 bug

- 没做完根因调查，不提修复方案。
- 读完错误与堆栈，不跳行。
- 先稳定复现；复现不了去收数据，不要猜。
- 查 `git diff`、新依赖、配置变化。
- 一次只改一个变量，验完再动下一个。

越觉得"这问题很简单""只有一处要改""要现在立刻修好"，越要走这套：
简单 bug 也有根因，乱撞比系统化慢。

## 收到批评：先验证再改

读完 → 用自己的话复述要求 → 对照代码库核实 → 判断这条建议对当前代码库是否成立 →
回应 → 逐条改、逐条验。

不说"你说得完全对""好点子""我马上改"——那是核实前就投降。站不住就用技术理由反驳，而不是照改。

有任何一条读不懂就停下来，把读不懂的一次问全，不要边改边问：
这些条目通常互相关联，部分理解等于做错。

## YAGNI 的边界（别拿它当偷懒的借口）

- 不等于忽略架构：把代码按职责切成文件和模块不算投机，它让后续改动更便宜。需要 ≥2 个实现的才叫接口（见「判据」）；文件与目录怎么划不需要理由。
- 不等于跳过错误处理：已知会发生的失败不是投机。
- 不等于拒绝零成本扩展：用 map 代替 switch 这种不花代价的事，做。
- 与 DRY 冲突时 YAGNI 优先：两个相似但不同的函数，好过统一到错的抽象下。

## 标准库缺位时

"标准库优先" + "不加依赖" 这两条，在标准库没有对应物时会把人推去手写轮子，而且通常没有测试。
实测案例：Node 无内置 CSV 解析器 → 59–125 行手写 RFC4180 状态机，支持分隔符嗅探、货币符号、
欧式小数逗号、UTF-16——需求里一个字都没提，且零测试。

1. 这个格式真的需要完整解析吗？单分隔符、无引号字段，`split` 就够。
2. 确实需要真解析器时，装依赖比手写便宜——这时"不加依赖"让位。
3. 手写的解析器必须有测试，因为没有任何人 review 过它的状态机。

## 不做

- 不发明需求。需求没写的格式、参数、编码，一律不做——常见越界项见上一节。
- 不为没出现的需求建抽象、配置项、插件系统、接口层。
- 不写没人要求的文档、README、类型体操，不为简单事实套一层封装。

## 已知取舍用 `ponytail:` 标注

故意砍掉真实角落（全局锁、O(n²) 扫描、启发式猜断）时，用 `ponytail:` 前缀注释写清上限和升级路径。
前缀必须是 `ponytail:`——`/ponytail-debt` 只扫这个前缀，写成 `ceiling:` 或 `TODO:` 就收不进账本。

## 优先级与冲突裁决

更具体的指令优先：仓库自带的 `AGENTS.md`、当前会话的规则、用户的直接要求，都覆盖本文件。

加载了 skill 时：skill 只提供做法细节，与本文冲突以本文为准——它是按需取用的补丁，不构成对每轮生效下限的覆盖。
例外只有一种：用户明确要求按某个 skill 的完整流程走，那时按那个 skill 走。
